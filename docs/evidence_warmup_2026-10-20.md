# Прогрев evidence-каталога — 20 октября 2026

Основа: main `b66189d` / PR50. Пользователь предложил прогревать каталог при
`/start`. Подготовка перенесена ещё раньше — в `RAGService.build()`, до возврата
из FastAPI lifespan и готовности app. Compose запускает bot после healthy app.
Команда `/start` не запускает повторную загрузку и не ждёт её для каждого чата.

## Изменение

`RelatedEvidenceIndex.warmup()` заранее загружает существующий каталог блоков,
отношений и локаторов, проверяет SHA-256 его исходных файлов и заполняет тот же
кэш, которым пользуются запросы. Прогрев работает под существующим `RLock`.
Каждое обращение по-прежнему проверяет файловые stamps. Изменение источника
требует повторной проверки SHA; замена каталога сбрасывает старые проверки.
Повреждённый или отсутствующий optional-каталог оставляет обычный retrieval
доступным и запрещает структурное расширение из старого снимка.

В лог попадают только время подготовки, количество валидных/невалидных
источников и статус загрузки. Модельных вызовов, переиндексации, embeddings,
изменения истории и отправки Telegram-сообщений прогрев не выполняет.

## Измерение и цена переноса

Один offline-прогон в работающем Linux app-контейнере с candidate resolver,
существующим каталогом и смонтированными исходниками:

| Операция | Время |
|---|---:|
| Полный прогрев, 10 валидных источников, 0 невалидных | 31,2518 с |
| Первый lookup после прогрева | 0,0414 с |
| Первый lookup другим, непрогретым resolver | 9,7028 с |

Это последовательный микрозамер; файловый кэш ОС и фоновая нагрузка не
контролировались. Он показывает перенос работы на startup, а не гарантированное
ускорение каждого ответа на 9,7 с. Полный прогрев проверяет все источники, даже
если первый вопрос использовал бы один. Startup I/O и пиковая память возрастают;
каждый файл хешируется существующим `read_bytes()`. После обновления каталога
во время работы первый запрос снова может потребовать загрузку.

## Оставшаяся проблема качества

Разбор одного медленного вопроса-перечня выявил 64,65 с обработки: исходная
подготовка 20,50 с, пять вызовов модели и четыре дополнительных поиска. В
исходной подготовке dense/translation заняли 5,13 с, lexical 1,36 с,
selection 13,90 с. Эти фазы не следует суммировать со временем всего графа.
Ответ перечислил специальные модели и пропустил базовые. Прогрев устраняет
холодную загрузку каталога, но не исправляет подбор полного перечня.

В принятом CHM-каталоге уже есть таблица Material: 31 последовательная строка,
пять столбцов, явная связь parent_table и сохранённые origins для rowspan.
Это точное DOM-извлечение с проверкой текущих исходных байтов, без флага
экспертной семантической проверки. Полная переиндексация не требуется для
наличия этой таблицы. Следующий исследуемый маршрут — получать общий каталог
для вопросов-перечней и затем выбирать детали. Он пока не включён в production.
Нельзя придумывать связь таблицы с подробными страницами моделей, назначать
версию по имени файла или трактовать Ground material как groundwater.

## Проверка Decisions API

[Официальный Decisions API](https://developers.openai.com/api/docs/guides/decisions)
поддерживает ограниченные суждения predicate/choice/score на `gpt-6-luna`.
Он может выбирать маршрут поиска; свободный ответ, аргументы tools и объяснение
по-прежнему требуют Responses. В трёх отдельных публичных пробах choice верно
выбрал catalog/procedure/comparison за 2,088 / 1,635 / 0,674 с; confidence
1,00 / 0,99 / 0,69. Это пилот, а не калибровка порогов или SLA.
Рабочий бот не переключён на Decisions. Пробы выполнены через HTTP, без
обновления закреплённого SDK 2.x: Python-пример docs требует SDK >=3.26.0.
