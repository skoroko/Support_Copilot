# HW 6.5 — ответы benchmark

Ниже сведены фактические ответы из `experiments/results.json`. В single-agent и
multi-agent использованы одни и те же пять вопросов, один mock-инструмент
`search_knowledge_base` и одна модель запуска (`gpt-5.4-mini` в сохранённом
прогоне). Оценка качества выполнена одним отдельным batched LLM judge по шкале
1–5. В таблице указаны `quality / total_tokens / latency_ms`.

## Сравнение по кейсам

| Кейс | Вопрос (кратко) | Single-agent: качество / токены / latency | Multi-agent: качество / токены / latency | Смысловое сравнение и итог |
|---|---|---:|---:|---|

Multi ошибочно ушёл в out-of-base fallback и сообщил, что подтверждённых сведений нет. Итог: single полностью ответил по KB, multi — нет. |

## Что именно произошло в двух провалах multi-agent

Case 01 и case 04 относятся к покрываемым mock-KB сценариям, а не к
out-of-base. Это видно по single-agent: в case 01 он сослался на
`KB/MIDAS-Licensing/activation.md`, а в case 04 объединил этот документ с
`KB/Support/diagnostics.md`. В обоих multi-ответах вместо этих фактов сказано,
что подтверждённых сведений нет, и приведены только `KB/Support/scope.md` и
`KB/Support/escalation.md`.

Следовательно, наблюдаемый факт — ошибочный переход multi-agent к
out-of-base fallback. В записях нет ошибки выполнения, а причины, по которым
маршрут выбрал fallback, не сохранены; `handoff_log` показывает обычную цепочку
`supervisor -> researcher -> supervisor -> writer`. Поэтому данные не дают
основания приписывать сбой конкретному prompt, retrieval или маршрутизатору.

## Aggregate summary

| Метрика | Single-agent | Multi-agent | Разница |
|---|---:|---:|---:|
| Средние токены на запрос | 1100.2 | 1470.2 | +370.0 (+33.63%) |
| LLM calls на запрос | 2 | 3 | +1 (+50%) |
| Latency p50 | 2248.48 ms | 3987.97 ms | +1739.49 ms (+77.36%) |
| Среднее качество | 5 | 3 | −2 |
| Handoffs на запрос | 0 | 3 | +3 |

Judge был выполнен одним отдельным batched вызовом. Его токены и вызов не
прибавлялись к метрикам сравниваемых реализаций. На этом наборе из пяти
одинаковых вопросов multi-agent не дал измеримого выигрыша: он потребовал
больше токенов и времени, добавил три передачи управления и получил более
низкое качество. Поэтому для текущего tight-coupled support-сценария выбрано
single-agent решение с тем же `search_knowledge_base`.
